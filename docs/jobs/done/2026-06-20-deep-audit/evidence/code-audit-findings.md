### [0] LIKE wildcard injection in search_term allows user to bypass search filtering
- sev(final): **MEDIUM** (orig MEDIUM, conf high) · logic correctness / data integrity
- loc: `app.py:1429-1449`
- whatWrong: User-supplied search_term is embedded directly into a LIKE pattern via f"%{term}%" (line 1431) before being passed as a bind parameter. DuckDB's LIKE engine interprets any % or _ characters already present in term as wildcards. A user who types % in the search box gets all rows (pattern becomes %%%, matching everything). A user who types _ gets any single-character match. The bind parameter prevents SQL injection but does not prevent wildcard mis-interpretation inside the LIKE expression.
- rootCause: There is no escaping of LIKE special characters (%, _, \) in the user's search term before constructing the pattern. Parameterized queries prevent code injection but do not sanitize pattern metacharacters within the value.
- verdict: The code at lines 1429-1449 of app.py confirms the finding. `search_term.strip().lower()` is placed directly into `f"%{term}%"` without escaping LIKE metacharacters (`%`, `_`, `\`) before the pattern is passed as a bind parameter to DuckDB. A user typing `%` produces pattern `%%%`, which matches every row in every searched column, returning all rows up to the LIMIT (10–100) regardless of what they actually typed. A user typing `_` gets any single-character match in any column. The parameterized query correctly prevents SQL injection but does nothing about wildcard interpretation inside the LIKE value itself. The severity is real but the security framing is overstated: the Explore tab is already password-gated on public deployments, and the LIMIT clause caps results at 100 rows — no additional data is exposed beyond what the tab already provides to authenticated users. The actual impact is incorrect search filtering (logic/correctness defect) rather than a meaningful security bypass. MEDIUM severity is appropriate but should be understood as a correctness bug, not an auth or data-exposure issue.

### [10] LIKE wildcard metacharacters not escaped in search_term
- sev(final): **LOW** (orig LOW, conf high) · logic correctness / silent wrong results
- loc: `app.py:1429-1449`
- whatWrong: The search term is converted to a LIKE pattern via `f"%{term}%"` without escaping SQL LIKE metacharacters `%` and `_`. Both collapse to a full scan up to the LIMIT, returning results that have nothing to do with the user's literal search intent. The query is parameterized so there is no SQL injection, but the user gets silently wrong results.
- rootCause: The code lacks a step to replace `%` with `\%` and `_` with `\_` in `term` before building `pattern`, and no ESCAPE clause is added to the LIKE predicate. DuckDB LIKE treats `%` and `_` as wildcards in the pattern regardless of whether the value is passed as a parameter.
- verdict: Lines 1429-1449 of /Volumes/ACLMR/jobads-dashboard/src/jobads_dashboard/dashboard/app.py confirm the finding. The user's search term is lowercased and stripped but otherwise placed directly into a LIKE pattern via `f"%{term}%"` with no escaping of `%` or `_` and no ESCAPE clause on the LIKE predicate. DuckDB treats `%` and `_` as wildcards in the pattern value even when it arrives as a bound parameter. A user entering `%` produces the pattern `%%%`, matching every non-NULL string across all search columns; `_` produces `%_%`, matching any string with at least one character. Both silently return results unrelated to the literal character the user intended to search for. There is no handling of these metacharacters anywhere in the surrounding code. The query is parameterized so there is no SQL injection risk, but the silent wrong-results behavior for LIKE metacharacters is real and reachable by any user of the search box.
